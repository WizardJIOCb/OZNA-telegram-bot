# 🔒 Критическое исправление блокировки дубликатов - Добавление даты в ключ блокировки

## Проблема

После исправления освобождения блокировок, дубликаты **всё ещё** создавались для рабочих активностей мобильной бригады.

### Анализ путём сравнения с работающей активностью "Дорога"

**Что работает** ("Дорога"):
- Колбэк: `cat_ТабДорога_yes`
- Ключ блокировки: `ozna_callback_{userId}_md5('cat_ТабДорога_yes')`
- Дубликаты **НЕ** создаются ✅

**Что НЕ работало** (Мобильная бригада):
- Колбэк: `cat_МобБриг_Электр_Досб_yes`  
- Ключ блокировки: `ozna_callback_{userId}_md5('cat_МобБриг_Электр_Досб_yes')`
- Дубликаты **создавались** ❌

### Корневая причина

Ключ блокировки создавался **БЕЗ учёта даты**:
```php
$lockKey = "ozna_callback_{$userId}_" . md5($category);
```

Это означало:
1. **Сценарий, который блокировался правильно** (быстрые двойные клики):
   - Клик 1 → Блокировка установлена → Обработка → Блокировка снята
   - Клик 2 (через миллисекунды) → **Заблокирован** (блокировка ещё активна) ✅

2. **Сценарий, который НЕ блокировался** (последовательные отправки):
   - Пользователь отправляет отчёт за 19.10.2025 → Блокировка установлена → Обработка → **Блокировка снята**
   - Пользователь **СРАЗУ** кликает ту же кнопку снова (за ту же дату) → Блокировка установлена заново → **Проходит!** ❌
   - Проверка дубликатов в `TabelEntry::addEntry` должна была его поймать, но...
   - **ЕСЛИ** второй клик произошёл **ДО** того, как первый сохранился в БД → Оба прошли проверку дубликатов ❌

## Решение

### Добавление даты в ключ блокировки

**Файл**: `c:\ozna_bot\CustomCommands\Handlers\TabelHandler.php`  
**Метод**: `routeTabelCallback`  
**Строка**: ~543

```php
// БЫЛО (неправильно):
$lockKey = "ozna_callback_{$userId}_" . md5($category);

// СТАЛО (правильно):
$date = $conversation->notes['tabel_data'] ?? date('d.m.Y');
$lockKey = "ozna_callback_{$userId}_" . md5("{$category}_{$date}");
error_log("🔒 LOCK DEBUG: Creating lock key with category='{$category}', date='{$date}'");
```

### Как это работает

**Сценарий 1: Двойной клик на один отчёт (та же активность, та же дата)**
```
Запрос 1: category='cat_МобБриг_Электр_Досб_yes', date='19.10.2025'
- Lock key = "ozna_callback_{userId}_md5('cat_МобБриг_Электр_Досб_yes_19.10.2025')"
- Блокировка установлена ✅
- Обработка...

Запрос 2 (быстрый двойной клик): category='cat_МобБриг_Электр_Досб_yes', date='19.10.2025'

- Не может получить блокировку ❌
- Пользователь видит: "⏳ Запрос обрабатывается"
- Дубликат **НЕ** создан ✅

Запрос 1 завершается:
- Блокировка освобождена
- Отчёт сохранён в БД
```

**Сценарий 2: Последовательные клики после завершения первого**
```

- Блокировка установлена ✅ (первая уже освобождена)
- Проверка дубликатов в TabelEntry::addEntry → Находит существующий отчёт ❌
```

## Многоуровневая защита

Теперь у нас **три** уровня защиты от дубликатов:

### Уровень 1: Callback-Level Locking (самый быстрый)
- **Где**: `TabelHandler::routeTabelCallback` (строка ~543)
- **Ключ**: `ozna_callback_{userId}_md5({category}_{date})`
- **Защита**: Блокирует одновременные запросы на тот же callback + дату
- **Timeout**: 3 секунды

### Уровень 2: Entry-Level Locking (в процессе создания)
- **Где**: `TabelEntry::addEntry` (строка ~1064)
- **Ключ**: `ozna_report_{userId}_md5({activityDisplayName}_{date}_{projectCode})`
- **Защита**: Блокирует создание дубликатов на уровне БД
- **Timeout**: 3 секунды

### Уровень 3: Database Duplicate Check (финальная проверка)
- **Где**: `TabelEntry::addEntry` → `DatabaseService::checkDuplicateActivityReport` (строка ~1083)
- **Защита**: Проверяет существующие записи в БД
- **Блокирует**: Логические дубликаты (та же активность, дата, проект)

## Почему предыдущее исправление не сработало

Предыдущее исправление (освобождение блокировок) было **правильным**, но **недостаточным**:

1. ✅ Блокировки правильно освобождались
2. ✅ Блокировки правильно блокировали быстрые двойные клики
3. ❌ **НО** ключ блокировки не учитывал дату
4. ❌ Если пользователь кликал дважды **после** освобождения первой блокировки
5. ❌ И **до** того, как первая запись сохранилась в БД
6. ❌ Оба запроса проходили проверку дубликатов (БД ещё пустая)
7. ❌ Оба запроса создавали записи → ДУБЛИКАТ

## Логирование для отладки

При тестировании проверьте логи на наличие:

1. **🔒 LOCK DEBUG**: Показывает создание ключа блокировки с датой
2. **⚡⚡⚡ MOBILE BRIGADE DUPLICATE CHECK**: Начало проверки дубликатов
3. **⚡✅ NO DUPLICATE** или **⚡❌ DUPLICATE FOUND**: Результат проверки
4. **🔒 MySQL callback lock acquired**: Блокировка установлена
5. **🔓 MySQL callback lock released**: Блокировка освобождена
